# Reglas Globales del Proyecto ME-SIM

- **Mobile & Tablet First**: Todo nuevo desarrollo, maquetación o refactorización de interfaz debe ser diseñado y optimizado prioritariamente para dispositivos móviles y tablets. Las vistas de escritorio se adaptarán de forma progresiva (`sm:`, `md:`, `lg:`).
- **Aesthetic Quality**: Mantener la estética premium con paleta oscura, acento amarillo corporativo (`#ffec00`), tipografía legible y microinteracciones fluidas.
- **Bilingüe (i18n)**: Todo texto nuevo, componente (botones, modales, alertas) o contenido creado debe estar disponible obligatoriamente en castellano y traducido correctamente al inglés respetando el sistema de internacionalización del proyecto.
- **Economía de Paddings**: En vista móvil, todos los contenedores de texto en el `body` deben mantener 10px de padding lateral (`.container-naked`), sin afectar a la estructura exterior de las tarjetas (`cards`). Dentro de las tarjetas se aplicará una separación interna equilibrada.
- **Iconografía Plana**: Todos los iconos deben ser planos, vectoriales y minimalistas. Queda estrictamente prohibido el uso de esqueumorfismo, sombras 3D excesivas o gradientes complejos en iconos.
- **Arquitectura Headless (Catálogo Externo)**: WooCommerce funciona exclusivamente como pasarela transaccional, libro de pedidos, clientes y cupones. No contiene catálogo de productos. Los planes provienen en tiempo real de la API de StrongeSIM y se insertan dinámicamente en WooCommerce sin `product_id`.
- **Integridad de Datos y Cero Mocks (Política Global)**: Queda estrictamente prohibido el uso de datos simulados (`mockData`), constantes ficticias hardcodeadas, respuestas sintéticas o fallbacks complacientes en cualquier parte del proyecto (especialmente en `src/app/admin/*`, `src/app/api/admin/*`, pasarelas de pago y catálogo). 
  - Todo componente o endpoint debe operar contra datos reales y oficiales de las APIs (StrongeSIM, WooCommerce, Stripe).
  - Los errores no se enmascaran: ante un fallo de red o respuesta vacía, el sistema debe aplicar el principio *Fail-Fast*, reflejando el error real o un estado vacío legítimo (`empty state`) en lugar de inventar contenido para rellenar la pantalla.
